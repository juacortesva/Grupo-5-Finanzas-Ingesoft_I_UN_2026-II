# ADR-0003: Alcance técnico del Walking Skeleton (Fase 0): endpoint inicial, identidad provisional y despliegue con Docker Compose

Autores:
 - @Estebandido-exe

Fecha: 2026-11-11

## Estado

Propuesto (pendiente de revisión del equipo)

## Contexto

El `ADR-0002` define que la construcción empieza con un *Walking Skeleton* (Fase 0): un hilo mínimo pero real que atraviesa React → FastAPI (`Router -> Service -> Repository`) → PostgreSQL, con migraciones de Alembic, generación de tipos con `openapi-typescript` y una primera prueba de `pytest` en verde.

Al revisar la documentación vigente (`ADR-0001`, `ADR-0002`, `01_Architectural_and_Detailed_Design.md`, `02_Interaction_and_Data_Design.md`, `estructura_repositorio.md`, `code_style.md` y `REQ-01`) se identificó que el diseño interno es suficiente (capas, modelo de datos, contrato de `evaluateProfile`), pero faltan cuatro decisiones técnicas sin las cuales cada integrante tendría que suponer por su cuenta:

1. **No existe contrato HTTP.** Las operaciones están definidas a nivel de clases (`completeSurvey`, `saveDraft`, `resumeSurvey`), pero ningún documento define rutas, métodos, cuerpos JSON ni códigos de estado. El `ADR-0002` pide "un endpoint inicial" sin decir cuál.
2. **No existe mecanismo de identidad.** El diseño establece que el `userId` proviene "del contexto de autenticación validado por el backend (dependencia de FastAPI)", pero el módulo de autenticación está declarado fuera del alcance de la Entrega 1 y la Entrega 2. Además, ningún módulo es dueño de `CLIENT` (tabla 2.3 del diseño 02).
3. **No existe definición de despliegue.** El `ADR-0002` habla solo de un entorno local. El curso exige desplegar en la VM compartida `vm-learn-engsw1-2026ii-g1`, en `/opt/projects-g1/team-5`, que comparten seis equipos.
4. **Inconsistencia documental sobre Docker.** La sección de recomendaciones de IA de `01_Architectural_and_Detailed_Design.md` afirma que el `ADR-0001` descarta Docker. El `ADR-0001` en realidad descartó la alternativa de microservicios por su sobrecarga operacional (CORS, comunicación entre servicios, orquestación de contenedores); no prohíbe empaquetar el monolito con Docker Compose.

Este ADR toma esas decisiones con el criterio del propio `ADR-0002`: el esqueleto debe ser mínimo y no debe inventar comportamiento de negocio que `REQ-01` no especifica.

## Decisión

### D1. Endpoint del esqueleto: reanudación de borrador (`resumeSurvey`)

El hilo conductor del esqueleto será la operación **`SurveyManager.resumeSurvey(userId)`**, ya diseñada en el diagrama 1.2 del diseño 02, expuesta como:

```
GET /api/surveys/draft
```

**Por qué esta operación y no otra:**
- Ya existe en el diseño (no se inventa una operación nueva).
- Es de solo lectura y no requiere reglas de negocio pendientes (umbrales, catálogo de preguntas).
- Atraviesa todas las capas: dependencia de identidad → `survey/router.py` → `survey/service.py` → `survey/repository.py` → PostgreSQL.
- Su rama "no hay borrador" es exactamente la respuesta que dará un sistema recién desplegado, y su rama "hay borrador" ejercita la serialización de `Decimal` (`option_value`), uno de los riesgos que el `ADR-0002` pide validar.

**Contrato HTTP:**

| Elemento | Especificación |
|---|---|
| Método y ruta | `GET /api/surveys/draft` |
| Identidad | Header `X-User-Id: <uuid>` (ver D2). El `userId` nunca viaja en la ruta, la query ni el cuerpo. |
| Cuerpo de la petición | Ninguno |
| `200 OK` — existe borrador | `{ "draft": { "surveyId": "uuid", "status": "DRAFT", "startedAt": "datetime ISO-8601", "updatedAt": "datetime ISO-8601", "answers": [ { "questionId": 1, "selectedOption": 2, "optionValue": "3.50" } ] } }` |
| `200 OK` — no existe borrador | `{ "draft": null }` |
| `401 Unauthorized` | Header ausente, con formato distinto a UUID, o UUID que no existe en `CLIENT`. Cuerpo con el formato por defecto de FastAPI: `{ "detail": "..." }`. |

**Notas del contrato:**
- `optionValue` se serializa como **cadena de texto** (comportamiento por defecto de Pydantic v2 para `Decimal` en JSON) para no perder precisión en JavaScript. Los tipos generados en TypeScript lo reflejan como `string`.
- Los nombres en JSON van en `camelCase` mediante el `CamelCaseSchema` de `code_style.md` §9.2; en Python se mantienen en `snake_case`.
- Se responde `200` con `draft: null` (en lugar de `204` o `404`) porque el diagrama 1.2 modela la ausencia de borrador como una respuesta normal ("empty resume"), no como un error, y porque un único tipo de respuesta simplifica los tipos generados.
- El cálculo de la "primera pregunta obligatoria pendiente" (diagrama 1.2) **no** forma parte del esqueleto: requiere el catálogo de preguntas, que aún no está especificado. Se agrega en el Slice 3.

Adicionalmente se expone un endpoint técnico, sin lógica de negocio:

```
GET /api/health  →  200 { "status": "ok", "database": "ok" }  |  503 { "status": "error", "database": "unreachable" }
```

Ejecuta `SELECT 1` contra PostgreSQL. Sirve para diagnosticar el despliegue; no requiere identidad.

### D2. Identidad provisional mediante header `X-User-Id`

Mientras no se diseñe el módulo de autenticación:

- Se crea la dependencia `get_current_user_id` en `backend/src/core/auth.py`. Lee el header `X-User-Id`, valida que sea un UUID y que exista en `CLIENT`, y devuelve el UUID. En cualquier otro caso responde `401`.
- Todos los routers obtienen el `userId` **únicamente** a través de esa dependencia, como exige la nota de diseño sobre autenticación del diseño 01.
- El modelo SQLAlchemy de `CLIENT` se ubica provisionalmente en `backend/src/core/identity.py`. Justificación: la identidad es transversal, `core/` es el lugar que `estructura_repositorio.md` reserva para "auth", y los módulos de dominio pueden importar de `core/` sin violar las reglas de dependencia. Ningún módulo de dominio escribe en `CLIENT`.
- El frontend envía el header con un `userId` de desarrollo definido en una variable de entorno de Vite (`VITE_DEV_USER_ID`).

**Este mecanismo NO es seguro:** cualquiera que conozca un UUID puede suplantar a ese cliente. Se acepta solo porque el sistema no contiene datos reales. Por eso queda prohibido cargar datos personales reales en cualquier entorno mientras D2 esté vigente. Cuando se diseñe la autenticación real (por ejemplo, JWT), solo cambiará `core/auth.py` y el cliente HTTP del frontend; los routers no se modifican.

### D3. Esquema inicial y datos de desarrollo

- **Migración inicial de Alembic:** crea las cinco tablas del modelo Entidad-Relación del diseño 02 §2.2 (`client`, `survey`, `question`, `answer`, `financial_profile`) con las restricciones de §2.2 y §2.4:
  - `survey.status` ∈ {`DRAFT`, `COMPLETED`}.
  - Índice único parcial `(client_id) WHERE status = 'DRAFT'`.
  - Único `(survey_id, question_id)` en `answer`.
  - Único `display_order` en `question`.
  - Único `client_id` en `financial_profile`.
  - Restricción de coherencia: si `evaluation_status = 'ERROR'`, entonces `assigned_category = 'UNDER_EVALUATION'` y `total_score` es nulo.
  - `weight`, `option_value` y `total_score` como `NUMERIC` (sin precisión fija mientras no se defina la escala de puntajes).
- **Ubicación de modelos:** `survey`, `question` y `answer` en `src/survey/models.py`; `financial_profile` en `src/categorization/models.py`; `client` en `src/core/identity.py` (D2).
- **Datos de desarrollo (*seed*):** un script `backend/scripts/seed_dev.py`, que se ejecuta manualmente y **no** forma parte de las migraciones. Crea un único cliente de prueba con UUID fijo `00000000-0000-0000-0000-000000000001` y correo `dev@example.com`. **No** crea preguntas: el catálogo (textos, opciones y pesos) sigue sin especificarse (diseño 02 §5).

### D4. Despliegue con Docker Compose

Se empaqueta el monolito definido en el `ADR-0001` con Docker Compose. No cambia la arquitectura: sigue siendo un solo backend, un solo frontend y una sola base de datos.

| Servicio | Imagen / build | Puerto expuesto en el host | Detalle |
|---|---|---|---|
| `db` | `postgres:16` | Ninguno | Datos en el volumen `db_data`. *Healthcheck* con `pg_isready`. |
| `backend` | `backend/Dockerfile` sobre `python:3.12-slim` | Ninguno | Al arrancar ejecuta `alembic upgrade head` y luego `uvicorn src.main:app --host 0.0.0.0 --port 8000`. Espera a `db` con `depends_on: condition: service_healthy`. |
| `frontend` | `frontend/Dockerfile` en dos etapas: `node` compila con `npm run build`; `nginx` sirve `dist/` | `${FRONTEND_PORT}:80` | `nginx.conf` redirige `/api/` a `http://backend:8000`. |

**Consecuencias de este diseño de red:**
- El navegador solo habla con nginx, en un único origen. Por eso **no se configura CORS** en FastAPI. En desarrollo local sin Docker, el *proxy* de Vite (`/api` → `http://localhost:8000`) cumple el mismo papel.
- La documentación interactiva que exige el curso (`ADR-0001`) se publica bajo el prefijo `/api` para que sea alcanzable a través de nginx: `FastAPI(docs_url="/api/docs", openapi_url="/api/openapi.json")`.

**Configuración y secretos:**
- Variables en un archivo `.env` en la raíz, que **no** se sube al repositorio (incluido en `.gitignore`): `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `DATABASE_URL` (`postgresql+psycopg://<usuario>:<clave>@db:5432/<base>`) y `FRONTEND_PORT`.
- Se versiona un `.env.example` con valores de ejemplo y sin contraseñas reales.

**Reglas por ser una VM compartida (seis equipos):**
- No se usa `container_name`: Compose antepone el nombre del proyecto (`team-5-backend-1`, etc.), lo que evita choques con otros equipos.
- Solo se publica un puerto en el host (`FRONTEND_PORT`, propuesto `3005`, pendiente de confirmación con el profesor).
- Se trabaja únicamente con comandos `docker compose` dentro de `/opt/projects-g1/team-5`. Quedan prohibidos los comandos globales (`docker system prune`, `docker stop $(docker ps -q)`, etc.).
- Actualización del despliegue: `git pull` seguido de `docker compose up -d --build`.

### D5. Contrato de tipos entre backend y frontend

- Script en `frontend/package.json`: `"gen:api": "openapi-typescript http://localhost:8000/api/openapi.json -o src/api/generated/schema.d.ts"`.
- El archivo generado **se versiona** en el repositorio. Así, la imagen del frontend compila sin necesitar el backend en ejecución, y cualquier cambio de contrato queda visible en el *Pull Request*.
- Regla: todo PR que modifique un `schemas.py` debe incluir el `schema.d.ts` regenerado.

### D6. Pruebas del esqueleto

Pruebas de integración en `backend/tests/integration/` contra PostgreSQL, usando una base de datos de pruebas separada (`TEST_DATABASE_URL`), nunca la del despliegue. Siguen la nomenclatura de `code_style.md` §8:

- `test_resume_survey_when_client_has_no_draft_then_returns_null_draft`
- `test_resume_survey_when_client_has_draft_then_returns_answers_with_decimal_as_string`
- `test_resume_survey_when_header_missing_then_returns_401`

### Criterio de salida de la Fase 0 (amplía el del `ADR-0002`)

1. Cualquier integrante clona el repositorio, crea su `.env` a partir de `.env.example` y ejecuta `docker compose up --build`.
2. Al abrir `http://localhost:<FRONTEND_PORT>`, la pantalla base de React muestra el resultado real de `GET /api/surveys/draft` para el cliente de desarrollo ("no hay borrador").
3. `GET /api/docs` muestra la especificación OpenAPI.
4. `pytest` pasa en verde.
5. El mismo despliegue funciona en la VM, en `/opt/projects-g1/team-5`.

Siguiendo la mitigación del `ADR-0002`:

## Alternativas consideradas

- **Alternativa A: solo un endpoint de salud (`/api/health`) como hilo conductor.**
  - *Por qué se descartó:* no atraviesa las capas `Router -> Service -> Repository` ni usa el modelo de datos ni la identidad, que son justamente lo que el `ADR-0002` pide validar. Se conserva solo como endpoint técnico de diagnóstico.
- **Alternativa B: usar `startSurvey` o `completeSurvey` como primer endpoint.**
  - *Por qué se descartó:* ambos dependen del catálogo de preguntas, y `completeSurvey` además de los umbrales de categoría. Ninguno de los dos está especificado, así que el esqueleto quedaría bloqueado o el equipo tendría que inventarlos.
- **Alternativa C: implementar autenticación real (registro, login y JWT) en la Fase 0.**
  - *Por qué se descartó:* no hay requerimiento ni diseño de autenticación, y construirla ahora contradice el mandato del `ADR-0002` de mantener el esqueleto mínimo. La dependencia de D2 aísla el cambio futuro a un solo archivo.
- **Alternativa D: exponer el backend con su propio puerto y habilitar CORS.**
  - *Por qué se descartó:* exige un segundo puerto en una VM compartida por seis equipos y reintroduce CORS, uno de los costos que el `ADR-0001` quiso evitar. Con nginx como único punto de entrada no hace falta.
- **Alternativa E: desplegar sin contenedores (procesos con `systemd` y PostgreSQL instalado en la VM).**
  - *Por qué se descartó:* obliga a instalar paquetes y servicios a nivel del sistema en una máquina compartida, con riesgo de afectar a otros equipos, y hace que el entorno local y el de la VM difieran.

## Consecuencias

### Positivas
- El esqueleto se construye **sin inventar reglas de negocio**: usa una operación ya diseñada y deja explícitos los supuestos técnicos.
- Se valida desde el primer día la serialización de `Decimal`, el paso a `camelCase`, la generación de tipos y la identidad por dependencia, que son los riesgos de integración señalados en el `ADR-0002`.
- El entorno local y el de la VM son idénticos (mismos contenedores), lo que reduce los errores del tipo "en mi máquina funciona".
- Un solo puerto expuesto y sin `container_name` minimiza los conflictos con los demás equipos en la VM.

### Negativas y mitigaciones (*trade-offs*)
- **Identidad insegura (D2).** *Mitigación:* uso exclusivo con datos ficticios; prohibido cargar datos personales reales; reemplazo acotado a `core/auth.py`.
- **`CLIENT` en `core/` es una ubicación provisional.** Si se crea un módulo de identidad o cuentas, habrá que moverlo. *Mitigación:* ningún módulo de dominio escribe en `CLIENT`; solo lo referencian por llave foránea.
- **Mayor complejidad de herramientas (Docker, nginx) para un equipo que no las domina.** *Mitigación:* la configuración la centraliza la tarea T1 y el resto del equipo solo necesita `docker compose up --build`.
- **El archivo de tipos generado puede quedar desactualizado.** *Mitigación:* regla de PR de D5.
