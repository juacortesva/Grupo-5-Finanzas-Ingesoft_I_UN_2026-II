## Contexto

El proyecto "Asesor Financiero Personal" requiere el desarrollo de una aplicación web interactiva trazada al requerimiento `REQ-01` (*Categorización Inicial de Situación y Hábitos Financieros*, reglas `BR-01` a `BR-06`), permitiendo el registro de usuarios, evaluación de perfiles financieros mediante encuestas breves, cálculo de métricas con precisión decimal exacta y visualización del resultado inicial.

El desarrollo está enmarcado en el curso de Ingeniería de Software I, lo que impone las siguientes restricciones y fuerzas en juego:
1. **Restricción de tiempo:** El desarrollo debe completarse en el transcurso de un semestre académico (aproximadamente 15 semanas) con dos entregas principales.
2. **Requisitos arquitectónicos:** La aplicación exige un desacoplamiento claro entre el cliente web y el servidor mediante una API REST, aplicando un diseño modular por dominio y arquitectura por capas (`router` $\rightarrow$ `service` $\rightarrow$ `engine`/`repository` $\rightarrow$ `models`).
3. **Precisión numérica y consistencia de datos:** Se requiere persistencia relacional con integridad referencial sólida (`client`, `survey`, `question`, `answer`, `financial_profile`) y manejo estricto de aritmética decimal exacta (`Decimal` / `NUMERIC`) sin errores de redondeo.
4. **Infraestructura de la cátedra y despliegue:** La base de datos PostgreSQL es provista de forma externa por la cátedra (**`g1-team-5-db`**), mientras que los servicios de aplicación deben ejecutarse de manera reproducible en desarrollo y desplegarse en la **VM del curso (`CentOS Stream 10`, directorio `/opt/projects-g1/team-5`)**.
5. **Documentación de la API:** La asignatura exige la especificación formal e interactiva de los endpoints del sistema.

## Decisión

Vamos a utilizar **React (con Vite y TypeScript)** para el Frontend, **Python con FastAPI** para el Backend, **SQLAlchemy y Pydantic** para ORM y validación de esquemas, y el servidor **PostgreSQL externo provisto por la cátedra (`g1-team-5-db`)** conectado mediante `DATABASE_URL` en `.env` (sin levantar un contenedor local de PostgreSQL). Para desarrollo reproducible y despliegue en la **VM del curso (`CentOS Stream 10`, directorio `/opt/projects-g1/team-5`)**, `docker-compose.yml` y los `Dockerfile` empaquetan únicamente los servicios **backend (FastAPI)** y **frontend (React/Vite)**.

## Alternativas consideradas

- **Node.js (Express) + React + PostgreSQL:** Evaluado por la unificación de lenguaje en todo el stack (Full-Stack JS/TS). Se descartó debido a la falta de un tipo `Decimal` nativo en JavaScript (riesgo de imprecisiones por punto flotante IEEE 754) y la necesidad de configurar manualmente la documentación OpenAPI y la validación de esquemas.
- **Java (Spring Boot) + React + PostgreSQL:** Evaluado por su madurez en el sector bancario y manejo de `BigDecimal`. Se descartó por la alta verbosidad del lenguaje y la extensa curva de configuración inicial, lo que representa un riesgo para el ritmo de entregas semanales.
- **Híbrido Microservicios (Spring Boot + FastAPI + PostgreSQL):** Evaluado para separar el Core de Negocio (Java) del motor de cálculo financiero (Python). Se descartó por la sobrecarga operacional (CORS, comunicación inter-servicio y orquestación compleja de múltiples contenedores) en un proyecto de un solo semestre, manteniendo `docker-compose.yml` acotado exclusivamente al backend y frontend conectados a `g1-team-5-db`.

## Consecuencias

### Positivas
- **Aritmética financiera exacta:** Manejo nativo de precisión decimal mediante `decimal.Decimal` de Python integrado con Pydantic y el tipo `NUMERIC/DECIMAL` de PostgreSQL (`g1-team-5-db`), eliminando errores de redondeo en puntajes y ponderaciones (`REQ-01`).
- **Documentación OpenAPI automática:** Generación interactiva de la especificación de la API (Swagger UI en `/docs`) a partir de las definiciones de Pydantic, cumpliendo directamente con los entregables de diseño y los contratos (`docs/contracts/`).
- **Validación de datos declarativa:** Pydantic valida automáticamente los tipos de datos en la entrada de las peticiones HTTP antes de que alcancen la capa de negocio.
- **Despliegue reproducible sin gestión de BD local:** Al contener únicamente backend y frontend en `docker-compose.yml` y `Dockerfile`, se garantiza paridad entre el entorno de desarrollo y la VM del curso (`CentOS Stream 10`, `/opt/projects-g1/team-5`) consumiendo la base de datos centralizada `g1-team-5-db`.
- **Facilidad de pruebas:** Ecosistema sencillo y rápido para ejecutar pruebas unitarias y de integración utilizando `pytest`.

### Negativas y Mitigaciones (Trade-offs)
- **Cambio de contexto de lenguaje (Context Switching):** El equipo usará TypeScript en el Frontend y Python en el Backend. *Mitigación:* Se utilizarán generadores de tipos (como `openapi-typescript`) para exportar automáticamente los esquemas de FastAPI a interfaces de TypeScript en el Frontend, garantizando un contrato de datos fuertemente tipado en ambos extremos.
- **Disciplina arquitectónica en FastAPI:** FastAPI no impone una estructura modular por defecto. *Mitigación:* El equipo adopta la organización modular por dominio definida en `docs/estructura_repositorio.md` y formalizada en `ADR-0003`: paquetes independientes por módulo (`backend/src/survey/`, `backend/src/categorization/`) con capas internas estrictas (`router.py` $\rightarrow$ `service.py` $\rightarrow$ `engine.py`/`repository.py` $\rightarrow$ `models.py`).
- **Dependencia de la base de datos externa (`g1-team-5-db`):** Todo entorno requiere conectividad y credenciales válidas en `.env` (`DATABASE_URL`). *Mitigación:* Documentar `.env.example` y sanear tablas residuales y `alembic_version` antes de inicializar las migraciones de Alembic en Fase 0.
