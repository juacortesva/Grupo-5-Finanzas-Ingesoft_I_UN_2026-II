## Contexto

El proyecto "Asesor Financiero Personal" requiere el desarrollo de una aplicación web interactiva que permita el registro de usuarios, evaluación de perfiles de riesgo mediante cuestionarios, cálculo de métricas financieras (proyecciones de ahorro/inversión con precisión decimal) y visualización gráfica del progreso de metas.

El desarrollo está enmarcado en el curso de Ingeniería de Software I, lo que impone las siguientes restricciones y fuerzas en juego:
1. **Restricción de tiempo:** El desarrollo debe completarse en el transcurso de un semestre académico (aproximadamente 15 semanas) con dos entregas principales.
2. **Requisitos arquitectónicos:** La aplicación exige un desacoplamiento claro entre el cliente web y el servidor mediante una API REST, aplicando patrones de diseño y arquitectura por capas (Controladores/Rutas, Servicios, Repositorios).
3. **Precisión numérica y consistencia de datos:** Se requiere persistencia relacional con integridad referencial sólida y un manejo estricto de aritmética de precisión fija para evitar errores de redondeo en operaciones monetarias.
4. **Documentación de la API:** La asignatura exige la especificación formal e interactiva de los endpoints del sistema.

## Decisión

Vamos a utilizar **React (con Vite y TypeScript)** para el Frontend, **Python con FastAPI** para el Backend, **PostgreSQL** como sistema de gestión de base de datos relacional y **SQLAlchemy** (junto con **Pydantic**) para la capa de ORM, acceso a datos y validación de esquemas.

## Alternativas consideradas

- **Node.js (Express) + React + PostgreSQL:** Evaluado por la unificación de lenguaje en todo el stack (Full-Stack JS/TS). Se descartó debido a la falta de un tipo `Decimal` nativo en JavaScript (riesgo de imprecisiones por punto flotante IEEE 754) y la necesidad de configurar manualmente la documentación OpenAPI y la validación de esquemas.
- **Java (Spring Boot) + React + PostgreSQL:** Evaluado por su madurez en el sector bancario y manejo de `BigDecimal`. Se descartó por la alta verbosidad del lenguaje y la extensa curva de configuración inicial, lo que representa un riesgo para el ritmo de entregas semanales.
- **Híbrido Microservicios (Spring Boot + FastAPI + PostgreSQL):** Evaluado para separar el Core de Negocio (Java) del motor de cálculo financiero (Python). Se descartó por la sobrecarga operacional (CORS, comunicación inter-servicio, Docker) que introduce en un proyecto de un solo semestre.

## Consecuencias

### Positivas
- **Aritmética financiera exacta:** Manejo nativo de precisión decimal mediante `decimal.Decimal` de Python integrado con Pydantic y el tipo `NUMERIC/DECIMAL` de PostgreSQL, eliminando errores de redondeo en proyecciones e intereses acumulados.
- **Documentación OpenAPI automática:** Generación interactiva de la especificación de la API (Swagger UI en `/docs`) a partir de las definiciones de Pydantic, cumpliendo directamente con los entregables de diseño del curso.
- **Validación de datos declarativa:** Pydantic valida automáticamente los tipos de datos en la entrada de las peticiones HTTP antes de que alcancen la capa de negocio.
- **Facilidad de pruebas:** Ecosistema sencillo y rápido para ejecutar pruebas unitarias y de integración sobre la lógica financiera utilizando `pytest`.

### Negativas y Mitigaciones (Trade-offs)
- **Cambio de contexto de lenguaje (Context Switching):** El equipo usará TypeScript en el Frontend y Python en el Backend. *Mitigación:* Se utilizarán generadores de tipos (como `openapi-typescript`) para exportar automáticamente los esquemas de FastAPI a interfaces de TypeScript en el Frontend, garantizando un contrato de datos fuertemente tipado en ambos extremos.
- **Disciplina arquitectónica en FastAPI:** FastAPI no impone una estructura de capas estricta por defecto. *Mitigación:* El equipo aplicará por convención un estándar limpio de separación de responsabilidades (`routers/` $\rightarrow$ `services/` $\rightarrow$ `repositories/` $\rightarrow$ `models/`).
